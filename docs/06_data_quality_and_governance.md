# Data Quality and Governance

## Validation Rules Catalog

| Rule Name | Table | Severity | Description |
| :--- | :--- | :--- | :--- |
| `PK_NOT_NULL` | All | **Critical** | Primary Keys (e.g., `patient_id`) must not be null. |
| `PK_UNIQUE` | All | **Critical** | Primary Keys must be unique within the dataset. |
| `VALID_GENDER` | `dim_patient` | Soft | Gender must be in ['Male', 'Female', 'Other']. |
| `AGE_POSITIVE` | `dim_patient` | Soft | Calculated age from `date_of_birth` must be > 0. |
| `VALID_WAIT_TIME` | `fact_appointments` | Soft | `waiting_time_minutes` must be >= 0. |
| `HR_RANGE` | `fact_wearables` | Soft | `avg_heart_rate` must be between 30 and 220. |

## Quality Gate Logic

Our validation engine implements the concept of **Quality Gates**. 
1. The engine evaluates all rules in the catalog against the incoming Pandas DataFrames.
2. Every failure is logged to the `data_quality_results` table for observability.
3. If a **Critical** rule fails (e.g., duplicate patient IDs), the gate closes. The pipeline raises an exception, aborts the load process, and updates the `pipeline_runs` status to 'Failed'.
4. If a **Soft** rule fails (e.g., impossible heart rate), the gate remains open. The pipeline drops the bad row or imputes a default value, logs a warning, and continues loading the healthy data.

## PHI Masking Strategy

Protected Health Information (PHI) poses a massive security liability. To enable analytics without exposing identities, we implement a masking strategy using **SHA-256 Hashing**.

During the transform phase (`transform.py`):
1. `first_name` and `last_name` are concatenated and passed through a SHA-256 hash function. The result is stored in `name_hash`.
2. `phone` is hashed and stored in `phone_hash`.
3. The original plain-text columns can be dropped before loading into the warehouse for higher security, or restricted via database Role-Based Access Control (RBAC).

*Note: Hashes are deterministic (the same name always produces the same hash), allowing data engineers to join tables on hashes without knowing the actual names.*

## Governance Disclaimer

**Warning**: The data generated by this pipeline is synthetic. However, the architectural patterns implemented (Hashing, Validation Gates, Secrets Management) are designed for real-world compliance frameworks like HIPAA and GDPR. Never commit real patient data or `.env` credential files to version control.

## Data Lineage Explanation

Data Lineage tracks the lifecycle of data from origin to destination. In this pipeline:

1. **Origin (Source APIs)**: Data originates from simulated JSON endpoints.
2. **Raw (Bronze)**: Data is persisted exactly as received in `data/raw/` to ensure traceability.
3. **Staging (Silver)**: Data is loaded into memory, where schemas are typed, dates are standardized, and PHI is hashed.
4. **Warehouse (Gold)**: Validated data is UPSERTed into the MySQL Star Schema (`hospital_db`). 
5. **Consumption**: The API queries the Gold layer to serve the Streamlit dashboard.

If an anomaly is found in the Dashboard, a data engineer can trace the lineage backwards: Dashboard -> API Query -> MySQL Fact Table -> Validation Logs -> Raw JSON, easily pinpointing where the data corruption occurred.
